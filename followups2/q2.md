Implemented and tested. The policy is a request option, defaulting to the old behaviour:

```ts
export type OverReceiptPolicy = "reject_batch" | "reject_line";
```

`reject_batch` stays the default deliberately: a lorry that arrived wrong is one event, and a clerk usually wants to stop and look. `reject_line` is for a consolidated delivery where one bad line should not hold up nine good ones.

**The modified planning loop** -- classify instead of throwing on the first offender:

```ts
const policy: OverReceiptPolicy = input.onOverReceipt ?? "reject_batch";
const accepted: Array<{ line: ReceiptLineInput; po_line: PoLineRow; isOver: boolean }> = [];
const refused: Array<{ po_line_id: number; reason: string; ordered: string;
                       already_received: string; attempted: string }> = [];

for (const line of input.lines) {
  const po_line = byId.get(line.poLineId)!;
  const after = money.add(po_line.received, line.receivedQty, 4, "received_qty");
  const isOver = money.cmp(after, po_line.ordered_qty) > 0;
  const authorised = Boolean(line.allowOverReceipt) && input.mayOverReceive;

  if (isOver && !authorised) {
    const detail = {
      po_line_id: line.poLineId, ordered: po_line.ordered_qty,
      already_received: po_line.received, attempted: line.receivedQty,
      reason: line.allowOverReceipt
        ? "requires the receipt.over_receive permission"
        : "resubmit with allow_over_receipt to accept it as an over-receipt",
    };
    if (policy === "reject_batch") {
      throw new ApiError(422, "over_receipt",
        `over-receipt on PO line ${line.poLineId}`, { ...detail, hint: detail.reason });
    }
    refused.push(detail);
    continue;
  }
  accepted.push({ line, po_line, isOver });
}

// A receipt that books nothing is not a receipt. Refusing here rather than
// writing an empty goods_receipts row keeps retry semantics simple: the
// transaction rolls back, the Idempotency-Key is released, and the caller can
// resubmit a corrected batch.
if (accepted.length === 0) {
  throw new ApiError(422, "over_receipt",
    "every line on this receipt was refused", { refused });
}
const planned = accepted;
```

**What changes in the `postEntry` call: nothing structural -- and that is the point.** `entryLines` is built from `planned`, which is now `accepted`, so a refused line contributes no `1300` leg, and `grossValue = money.sum(entryLines.map(l => l.amount))` sums only what was accepted. The GR-IR credit is therefore `-grossValue` over the same list. The entry balances by construction, not by a separate correction.

The failure mode this avoids: if `entryLines` had been built from `input.lines` while movements came from `accepted`, the entry would credit GR-IR for goods never received. `assert_movement_posted` would not catch it -- it compares each movement to its own `1300` leg, and every *present* movement would still tie; the extra `1300` leg would have no movement at all. `ledger_entry_complete` would still see sum zero. So nothing would fire, and Inventory would be overstated silently. Building both from one list is what closes that.

Measured -- PO with line A ordered 100 @ 2.50 and line B ordered 10 @ 4.00, receipt of 40 and 12:

```
[batch] 40 good + 12 over -> 422 over_receipt        (good line not booked; PO stays APPROVED)
[line]  201 policy=reject_line booked=1 refused=1 gross=100.00
[line]  refused: {"po_line_id":4,"ordered":"10.0000","already_received":"0",
                  "attempted":"12","reason":"resubmit with allow_over_receipt ..."}
[entry 2] 1300 100.00, 2100 -100.00 | lines=2 sum=0.00
[entry] reconciliation delta=0.00 status=TIES
[all-refused] 422 over_receipt, refused=1        (no empty goods_receipts row left behind)
[authorised] 201 over_receipt=true refused=0
```

`gross_value` is `100.00`, not `148.00`. Response shape adds `refused[]` and `policy`; `lines[]` carries only what was booked. Five tests, all green.
