**The line that prevents it** is the `ORDER BY` inside the single locking statement, and specifically that `LockRows` sits *above* `Sort` in the plan:

```ts
await tx.query(
  `SELECT 1 FROM stock_balances b
    WHERE (b.product_id, b.warehouse_id) IN
          (SELECT l.product_id, l.warehouse_id FROM sales_order_lines l WHERE l.so_id = $1)
    ORDER BY b.product_id, b.warehouse_id
    FOR UPDATE`, [soId]);
```

`EXPLAIN` on your exact case -- one product, two warehouses, listed WH2 first:

```
LockRows
  ->  Sort
        Sort Key: b.product_id, b.warehouse_id
        ->  Nested Loop  ...
```

Locks are taken in the order tuples leave `Sort`, never in scan or insertion order. Seeded so insertion is the reverse of sort order:

```
 line_id | wh  | product_id | warehouse_id
       1 | WH2 |          4 |            2
       2 | WH1 |          4 |            1
```

`(4,1)` -- WH1 -- locks first. Same product, so `warehouse_id` is the tiebreaker, and it being the *second* sort key is what makes this case work rather than work by luck.

**The trace.** (1) `SELECT status` -- no lock, a 404/409 gate. (2) The statement above; both rows pinned in one statement, so no other transaction can interleave *between* the two locks. (3) Availability is read only now. (4) Reservations are inserted -- new rows, no conflict. (5) `UPDATE sales_orders`.

A concurrent order touching one of those rows either waits at step 2 or holds it and we wait. Either way both transactions acquire `(4,1)` before `(4,2)`, so no cycle can form.

**The bug, reintroduced:**

```ts
const lines = await tx.query(
  `SELECT id, product_id, warehouse_id FROM sales_order_lines
    WHERE so_id = $1 ORDER BY id`, [soId]);
for (const l of lines.rows) {
  await tx.query(`SELECT 1 FROM stock_balances
                   WHERE product_id=$1 AND warehouse_id=$2 FOR UPDATE`,
                 [l.product_id, l.warehouse_id]);
  // ... insert this line's reservation, then next line
}
```

`ORDER BY id` is insertion order -- the caller's order -- so two orders that list the same two SKUs oppositely lock oppositely. Measured, A listing WH1 first and B listing WH2 first:

```
PER-LINE LOOP:              order A: 40P01 deadlock detected   order B: committed
SINGLE ORDERED FOR UPDATE:  order A: committed                 order B: committed
```

| | A (WH1, WH2) | B (WH2, WH1) |
|---|---|---|
| t1 | locks `(4,1)` | -- |
| t2 | -- | locks `(4,2)` |
| t3 | wants `(4,2)` -> waits on B | -- |
| t4 | -- | wants `(4,1)` -> waits on A |
| t5 | `40P01`, rolled back | commits |

I also ran the lock-then-insert variant, since that is the shape a real loop takes: A inserts its WH1 reservation, then deadlocks, and the rollback discards it cleanly -- only the winner's rows survive. So the damage is a failed order and a wasted round trip for a satisfiable purchase, not corrupt data.

Two things the loop also loses: an N-line order holds its first lock across N-1 further round trips; and retry does not fix the cause, since clients that consistently disagree keep colliding. `no_oversell` never fires -- a deadlock is not an oversell. Only ordering protects liveness.
