**(1) The SQL, three phases.** Balance locks come *first*, in the same `(product_id, warehouse_id)` order `confirmSalesOrder` uses:

```ts
export async function expireReservations(tx: Tx, batch = 500): Promise<number> {
  const candidates = await tx.query<{ id: string }>(
    `SELECT id FROM stock_reservations
      WHERE status = 'HELD' AND expires_at < now()
      ORDER BY expires_at LIMIT $1`, [batch]);
  if (candidates.rowCount === 0) return 0;
  const ids = candidates.rows.map((r) => r.id);

  await tx.query(
    `SELECT 1 FROM stock_balances b
      WHERE (b.product_id, b.warehouse_id) IN
            (SELECT r.product_id, r.warehouse_id FROM stock_reservations r
              WHERE r.id = ANY($1::bigint[]))
      ORDER BY b.product_id, b.warehouse_id
      FOR UPDATE`, [ids]);

  const done = await tx.query(
    `WITH claimed AS (
       SELECT id FROM stock_reservations
        WHERE id = ANY($1::bigint[]) AND status = 'HELD' AND expires_at < now()
        FOR UPDATE SKIP LOCKED)
     UPDATE stock_reservations s SET status = 'EXPIRED'
       FROM claimed c WHERE s.id = c.id AND s.status = 'HELD'`, [ids]);
  return done.rowCount ?? 0;
}
```

Phase 1 is unlocked and bounded. Phase 3's `status='HELD'` re-check under the row lock is the real guard: a checkout that reached `CONSUMED` first drops out of the `WHERE`, so we never transition out of a terminal state -- which matters because `reservation_state_machine` raises `ERP08` on `OLD.status <> 'HELD'` and would kill the whole batch. `SKIP LOCKED` lets several schedulers run. Nothing touches `reserved_qty`: `sync_reserved()` recomputes it as an absolute `SUM(qty) WHERE status='HELD'`, so a retried batch lands on the same value.

**Lock ordering, and what breaks without it.** The natural sweep is reservations-first, letting the trigger take balances as it goes -- ordering locks by `expires_at`, which has no relation to `(product_id, warehouse_id)`. Any writer that *does* sort its locks disagrees as soon as a batch spans two SKUs. Sleeps did not reproduce it, so I forced the interleaving -- `A=(prod 4,wh 1)`, `B=(prod 5,wh 1)`, sweep visiting B first:

```
1. T1 (sweep, no balance lock) expired res on B  -> holds balance B
2. T2 (confirm) locked balance A in sorted order -> holds balance A
3. T1 wants balance A (held by T2)
4. T2 wants balance B (held by T1)
   T1: 40P01 deadlock detected      T2: ok
```

What breaks is liveness, not the quantity invariant -- `no_oversell` never fires, since a deadlock is not an oversell. Phase 2 fixes it by making the sweep name and sort its rows.

**(2) Release, or convert to backordered?** Neither -- and this is the part I had to check rather than assume. `sales_order_line_status.backordered_qty` is `qty - fulfilled_qty`, so nothing needs converting:

```
BEFORE expiry: qty=8 fulfilled=0 backordered=8 status=OPEN  holds=5.0000  SO=CONFIRMED
               balance: on_hand=5 reserved=5 available=0
sweep expired 1
AFTER  expiry: qty=8 fulfilled=0 backordered=8 status=OPEN  holds=0        SO=CONFIRMED
               balance: on_hand=5 reserved=0 available=5
```

The line read 8 backordered while 5 were held, so the field is really "not yet shipped", not "not covered by stock"; the genuine figure (3) exists only in the confirm response. Two gaps follow, neither fixed: the view should expose `held_qty` and `uncovered_qty = qty - fulfilled_qty - held_qty`, and `sales_orders.status` should not stay `CONFIRMED` once no live hold exists.

**(3) Ledger: no entry, and that is not an omission.** Measured: `ledger_entries 1 -> 1`. A reservation is a promise about future stock, not an economic event -- nothing moved, no obligation arose or was discharged. An entry here would book a transaction that never happened and break the subledger-to-1300 tie, since no movement matches it. The audit distinction lives in the enum: `RELEASED` (someone acted) versus `EXPIRED` (the TTL lapsed). Honest weakness: `forbid_mutation` covers `ledger_entries`, `ledger_lines` and `stock_movements` but **not** `stock_reservations`, so that history is convention, not enforcement.
